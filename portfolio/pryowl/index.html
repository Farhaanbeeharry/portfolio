Pryowl

June — July 2026 Farhaan Beeharry
web app saas react supabase postgresql e-signature ai copilot
Pryowl started as a survey builder and grew into a data-collection and document platform. Authors design forms in a visual builder with genuinely advanced logic, publish them with intelligent gating, auto-mark them as quizzes, analyse the results across nine chart types — and, in the same workspace, send PDFs out for e-signature. It is React on Supabase, with the rules that matter living in Postgres rather than in the screen that happens to be showing them.

1 · Hoot, the owl in the corner
Hoot is an AI copilot you talk to in a chat. Describe what you want to ask and it returns a complete survey — title, questions, options, settings — then keeps editing as you refine, and names exactly what it changed each turn.

The interesting part is what surrounds the model rather than the prompt:
  • The reply is produced under a structured-output schema, so a valid survey shape comes back or the call fails — the client never parses prose hoping for JSON
  • The schema enum is deliberately a superset of what the model is asked to generate. It also accepts display-only elements the author added by hand, because constrained decoding would otherwise coerce an image or a link into some answerable type and destroy it on the round trip
  • Every reply is diffed deterministically against the previous survey by stable question id, and the chat shows that diff — "Q3: added", "Q5: changed" — prefixed with real question numbers. What the user is told changed is computed, not narrated by the model
  • A guard re-inserts any question the model silently dropped, at its original relative position, matching by id or by exact text so a legitimately reworded question is not duplicated. Losing a question you did not ask to remove is the failure that makes an AI editor untrustworthy
  • The API key is a server-side secret in an edge function, the function runs under the caller's JWT, and the monthly allowance is checked there — so the free tier's zero-Hoot limit is enforced where the spending happens rather than by hiding a button
  • The whole conversation is persisted per survey in its own workspace-scoped table, so the next person to open the builder sees the history and can continue it — and that table is never reachable from the public fill page
  • Hoot's tone is a per-user setting — hilarious, professional, sarcastic and others — and it changes only how Hoot talks, never the survey it writes

2 · The builder
Twenty-one question types: short and long answer, e-mail, number, phone, date, time, single and multiple choice, dropdown, yes/no, consent, star rating, linear scale, NPS, matrix grids, section breaks, image upload, image URL, link and file upload.

On top of them, three layers of structure that most builders treat as one:
  • Conditional logic — show or hide a question on an earlier answer, stored as a small object rather than as code
  • Skip logic and branching — an answer can jump the respondent to a named question, to the next one, or to the end
  • Sections and paging — a survey is a freely-ordered mix of standalone questions and sections containing questions, and sections and questions share one global position sequence, so the interleaved order the author sees is the order that is stored. The survey then renders all on one page, one question per page, or one section per page, and a timer can hang off whichever of the two is the paging unit

3 · A quiz is a setting, not a second product
Correct answers are stored per question, and — critically — never sent to the browser: the public fetch omits the column entirely, and grading happens inside a server-side function. The answer key cannot be scraped from the page, because it was never on it.

Grading is then configurable per question rather than globally: normal, scheme (with an optional penalty for wrong answers), formula, or manual. Anything non-objective is left pending for a human marker with a responses.mark permission, each answer carrying its own maximum, automatic marks, awarded marks, who graded it and when. A respondent's score comes back with the number of answers still pending attached, so "you scored 6" and "we have not finished marking you" are never confused for each other.

A respondent can opt in to receive their result by e-mail, and chooses between a score and a full per-question breakdown — which is generated by a marker-gated function rather than assembled in the browser.

4 · Publishing, and the honest cases
  • Response caps close a survey automatically. "Completed" means the response actually ended, and an in-progress attempt is allowed to finish once the cap is reached — only new opens are blocked. Kicking somebody out mid-form to enforce a quota loses their answers and teaches them not to start one again
  • Save and continue later keeps a part-finished response on the respondent's own device. It is client-side by design: a half-answered form is the respondent's, and storing it server-side would mean collecting answers from somebody who has not submitted anything
  • One-per-browser and one-per-e-mail submission limits, anonymous responses where the survey allows them, and attempt timers with a clear notice when time is capped
  • A live survey can be cancelled without destroying its responses — closing a survey and deleting its data are different intentions
  • Every response is stored as an immutable snapshot of the survey at submission time, so editing a question next month never rewrites history or corrupts old analytics

5 · Sign — a second product on the same foundations
An owner uploads a PDF and places, per signer, exactly where each person must sign: signature, initials, date and free-text fields, with coordinates normalised 0..1 against each page so the placement survives any render scale. Multiple signers each fill only their own fields, and the owner downloads the finished, flattened PDF.

It deliberately mirrors the survey architecture — workspace scoping and RBAC through the same helpers, atomic writes through a security-definer RPC, private storage buckets guarded by policies on storage.objects — and then makes one decision of its own worth stating:

A signer does not need an account. The 64-hex token in the signing link is the capability: unguessable, issued per signer, and revoked by voiding the document. Storage nevertheless stays closed to anonymous callers — the signing page reaches the original PDF and uploads its signature images through an edge function that validates the token with the service role and hands back short-lived signed URLs. No anonymous policy was added to storage to make signing work.

Signers still get a history: matching is done by e-mail, so somebody who signed anonymously today and creates an account months later still finds every document they signed — and the same call claims those rows, so the link survives a later change of address.

6 · Workspaces and a permission system that cannot be incoherent
Teams collaborate in workspaces with fine-grained RBAC across 24 permissions, and the scoped ones are tri-state rather than boolean — None / Own / All — so a member can be allowed to edit their own surveys while only viewing everyone else's.

Two properties make it hold up:
  • Implications are enforced. Granting "publish own surveys" silently raises "view own surveys", because the first is meaningless without the second. A role cannot be saved in a state that describes a person who can publish something they cannot see
  • The database re-checks it. A status change on a survey fires a trigger that demands the publish permission through the same can_act_on_resource() helper the UI uses — and because the trigger is SECURITY INVOKER, it still sees the real caller even when the change arrives through a security-definer RPC. Ordinary content edits are untouched, since it only acts when the status actually changes

Plan tiers cap workspaces per account and surveys per workspace — one and one on Free, rising through Pro and Business — and the caps are functions in the database with the client gating the UI on the same numbers, not instead of them.

The rest
  • Analysis — nine chart types (bar, stacked bar, line, pie, polar area, radar, gauge, a data table and a per-question chart picker), per-question summaries, individual response inspection, and CSV and PDF export
  • An AI summary of free-text responses, on the same edge-function pattern as Hoot
  • Respondents — invite by e-mail from inside the app, and a "my responses" area where somebody can find their own submissions
  • Branding — per-workspace colours, logos and a custom start screen; reusable templates
  • Accounts — two-factor authentication, OTP verification and OTP password reset, ownership transfer, workspace icon and colour
  • Platform — in-app notifications, a marketing site with features, pricing, comparison, e-signature and Hoot pages, EN/FR and dark mode, both driven by CSS custom properties rather than a component-level theme
