Web app & UI/UX

Lokal

July — August 2026 Farhaan Beeharry
web app directory react 19 typescript supabase full-text search mauritius
Lokal inverts the usual directory. A customer does not search for a business name — they search for the thing they need. Brochette. Mechanic. Hardware. Lokal answers with the businesses near them that actually have it, says whether each one can serve them right now, and gives them a way to reach it without making a phone call.

For a small Mauritian business it is an affordable digital presence: a profile, a catalogue, a live availability status, direct chat with customers, and — on the higher plan — online orders and business insights.

Lokal never handles money between a customer and a business. There is no payment gateway and no commission. A buyer settles directly with the seller; the platform records the order and its fulfilment state and nothing more. The only money Lokal collects is the seller's monthly subscription, transferred out of band by MCB Juice and verified by hand by an administrator. That decision is the reason the product is small enough to be trustworthy: an entire class of custody, refund and chargeback problems simply does not exist in it.

The application is React 19 and TypeScript on Supabase, in a clean, feature-sliced architecture: each feature owns its domain (types, Zod schemas, pure rules), application (TanStack Query hooks), infrastructure (the only layer permitted to talk to Supabase) and presentation layers. Rules such as "may this seller submit for activation" and "is this availability status still trustworthy" are plain, React-free, unit-tested functions. It has four surfaces: the public website, the visitor experience, the seller portal with its seven-step onboarding wizard, and the admin CRM.

1 · Finding the thing, not the shop
Because the query has to reach further than the business row, every business carries a weighted tsvector that triggers rebuild from both the business and its products: weight A for the name and the seller's own tags, B for category, town and address, C for the description, and D for every product name and description. A shop called Chez Ahmed selling brochette poulet is therefore found by "brochette" — and a shop actually named Brochette Express still outranks it, because the name is weighted above the catalogue.

Three details make that search behave the way a person expects:
  • The query is built as a prefix match, so "brochet" finds "brochettes". Nobody finishes the word before the results should start being right
  • The text-search configuration is simple, not english. The content is a mix of English, French and Kreol, and an English stemmer mangles the latter two — the prefix query recovers the partial matching the stemmer would otherwise have given
  • The RPC returns the unpaginated total alongside each row, so a page of results and the count above it cost one round trip rather than two queries that can disagree

Sellers add unlimited free-form tags — their own vocabulary, bridging a fixed category taxonomy and the words a customer actually types. Normalisation (trim, lowercase, de-duplicate, forty-character cap) is a Postgres trigger rather than a form validator, so an API caller cannot bypass it; the form applies the identical rule, so the chip a seller sees is the chip that gets stored.

2 · Open now, and how much to trust it
Opening hours are a schedule. The availability status is what the seller says is true now — open, closing soon, busy, temporarily closed, delivering, available now — and the two are different kinds of claim.

A seller-set status wins while it is fresh. After twelve hours it is discarded, not downgraded: a badge reading "open" that nobody has touched since yesterday evening sends someone across town to a locked door, which costs more trust than showing no badge at all. Past that window the profile falls back to the published hours, and the interface says which of the two it is showing — an inferred status is never presented as the business's own word. A test covers exactly that: that the provenance line cannot misattribute an inferred status to the seller, and that a stale note is dropped along with the status it belonged to.

3 · The plan is a capability, not a label
Two monthly subscriptions, priced for small businesses: Basic at Rs 390 and Advanced at Rs 590. Both carry the profile, catalogue, photos, hours, live availability, chat, reviews, promotions and GPS search; Advanced adds online orders, order management and business insights.

The gate is enforced twice, independently. The client rule lives in subscriptions/domain/plan.ts; the database has its own, because hiding a button must never be the only thing standing in the way — the RLS insert policy on orders refuses an order placed against a business that is not on a live Advanced subscription. Prices are read from platform_settings, so an operator changes them without a deploy, with a constant as the fallback until that fetch resolves.

4 · A seller cannot publish themselves
A business walks draft → pending_activation → active, with suspended as an admin action. The WITH CHECK clause restricts a seller to the first two states, and publication happens only inside approve_activation_request(), which is gated on is_admin(). There is no path from the seller portal to a published listing that does not pass through a person.

Publication is not permanent either. Each verified payment rolls subscription_expires_at forward one month — and renewing early extends the period rather than truncating it, so paying ahead is never punished. A sweep unpublishes anything past its paid-through date. Because a sweep runs on a schedule and the truth changes on a timestamp, the capability gate reads the expiry date rather than the stored status, and so stays correct in the gap between the two.

5 · Ordering without a payment processor
An order walks pending → awaiting payment → payment verified → fulfilling → completed, with cancelled reachable from any state before completion. Two modelling decisions matter more than the flow:
  • Line items snapshot the product name and unit price as they were at order time, and the product foreign key is on delete set null. Editing a price next week, or deleting the product entirely, cannot rewrite what a customer agreed to last week
  • The total is recomputed server-side from those snapshots when the order is placed. The number the client sends is not the number that is stored

Messaging is one thread per (business, buyer) pair, enforced by a unique constraint — reaching out to the same business twice reuses the conversation rather than forking it. Unread state is two "last read" timestamps kept on the conversation itself, one per side, so an inbox badge is a single indexed read instead of a scan across messages; a trigger stamps the sort key and the sender's own read marker on every insert. There is no anonymous path into it — the public contact form remains the separate, unauthenticated channel.

6 · The preview problem, solved by deletion
The seller's preview step and the public profile page are rendered by the same component. Not a shared design, not a synchronised pair — one file, two routes. What a seller previews therefore cannot drift from what visitors get, and the entire genre of "but it looked fine in preview" bug has nowhere to live.

7 · Two languages, enforced by the test suite
English and French across ten i18next namespaces, with no user-facing string hardcoded — including the legal documents, which are structured data rendered generically rather than prose in a component. A test fails the build if the two languages drift in key coverage, if a French string is left empty, or if the legal section ids stop matching between them, which would produce dead in-page anchors in one language only.

Errors carry translation keys rather than sentences — a service throws AppError('storage.file_too_large') and the presentation layer resolves the copy — so a French-speaking user never sees a raw English Postgres message.

Engineering
  • One home per kind of state: server state in TanStack Query, session in a push-based context fed by Supabase's own subscription, language and nav in Zustand, search filters in the URL so a result set is linkable, bookmarkable and back-button safe. Multi-select categories are repeated ?category= params, not a comma-joined string that has to be re-parsed
  • One source of truth per concept: routes, query keys, design tokens and prices are each defined in exactly one place
  • 98 tests aimed at where a mistake would be silent — the staleness rule, the plan gate including the lapsed-but-not-yet-swept window, contact-link building and the digits-only normalisation wa.me requires, opening hours parsed from untrusted JSON including past-midnight spans, the activation gate, and "as from" versus fixed price rendering with a fallback that avoids showing "Rs 0"
  • Environment variables are validated at startup, so a bad value fails loudly instead of surfacing deep inside the Supabase client. Only the publishable key is ever in a VITE_ variable — Vite inlines those into the bundle, and RLS rather than key secrecy is what protects the data
  • Type generation writes through a script rather than a shell redirect. A redirect truncates the target before the CLI runs, so one failed generation destroyed the types and surfaced as hundreds of unrelated type errors; the script buffers, sanity-checks, then writes
  • Accessibility is built in rather than audited afterwards: skip links, visible focus rings, wired label / hint / error relationships, a category filter that is a real listbox with aria-multiselectable instead of a menu, role="alert" and role="status", skeletons hidden from screen readers behind a single announcement rather than a wall of empty boxes, and prefers-reduced-motion honoured globally
