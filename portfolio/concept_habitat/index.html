Concept Habitat

October 2025 — September 2026 Farhaan Beeharry
website event crm mobile app react flutter supabase postgresql
Concept Habitat is a home & lifestyle company trading since 1986 out of a showroom on Pasteur Avenue in Rose Hill, Mauritius. It sells and installs decorative surfaces and finishes — SPC flooring, wall cladding, bamboo charcoal board, decorative acrylic, aluminium profiles, faux stone, glass blocks, water features, artificial plants — for residential, commercial, industrial and corporate projects, with architects, interior designers, landscapers and builders in house.

I built three products for them across eleven months, and each one exists because the one before it was in use:
  • The public website (October 2025) — the storefront: five pages, an eighteen-category catalogue, and a contact form that actually delivers
  • After Hours — the event CRM (June 2026) — a staff-only React + Supabase CRM with a public visitor-registration form, built for an invite-only evening at the showroom
  • The internal mobile app (September 2026) — a Flutter application covering the whole business: showroom, sales, design, survey, quotation and installation teams
The third is the reason this is one case file rather than three. The CRM was live, with real visitor records on it, when the mobile app's schema had to land on the same Supabase project — and the two applications do not describe a person the same way. That migration is the most interesting thing on this page, and it is section 4.

Common ground. All three carry the same brand: a single brass-gold accent over a warm neutral on the website (#bb9a65), copper over near-black in the CRM (#c19a6b), gold over deep green in the app (#c4a452). Two of the three run on Supabase, one Postgres project, one set of Row Level Security policies.

1 · The public website
A hand-built static site on a Bootstrap 5 theme — no CMS, no build step, deployed to shared cPanel hosting. Five pages: home, about us, products, contact us, and a coming-soon page holding the e-catalogue slot until the catalogue itself is ready.

The home page runs a three-slide hero, each slide with its own line and its own Book Consult call to action (“Living spaces reinvented”, “Elevating every space”, “Greenery and serenity”); a since 1986 studio section that names the four segments the company works in — commercial, industrial, residential, corporate; the four-step process in the company's own words (Inquiry & Advisory Meeting → Client orientation → Confirmation Notice → Delivery & Installation); six reasons-to-choose cards; a founder's note from Jemilin E. William; and a newsletter sign-up.

The products page carries eighteen categories, each photographed — aluminium profile, artificial plants, bamboo charcoal board, carpet tiles, decorative acrylic sheets, faux stone, flexible concrete stone, fluted bars, flower pots, foam blocks, glass blocks, pebbles & stones, PU cladding, simulated fireplace, SPC flooring, wall dividers, wallpapers, water fountain — and the same eighteen are mirrored into the header's mega-menu, so a visitor can jump to a material from any page. The about page carries a draggable before/after comparison slider over a real installation, which is the single most persuasive thing on the site and cost about twenty lines of jQuery.

Motion is deliberate rather than ambient: GSAP with ScrollTrigger and SplitText for the headline reveals, AOS for section entrances, Swiper for the sliders, Isotope for the filterable grids, Magnific Popup for lightboxes, Morphext for the rotating words. Contact details — Pasteur Avenue, +230 490 6060, info@concepthabitat.mu — sit in the pre-header on every page, alongside a maps embed, WhatsApp and Facebook on the contact page.

The contact form is the only server-side part of the site, and it is the part that had to be right:
  • send.php answers JSON only. Display errors are off and everything is written to a log file instead, because a single PHP warning printed above the payload breaks the response the page is parsing — and the visitor sees a form that failed for no reason
  • Every field is validated twice: jQuery Validate in the browser, then again on the server — required, format, and a length cap per field (100 for names, 255 for email and subject, 30 for phone, 2,000 for the message)
  • Input is normalised rather than trusted: tags stripped, whitespace collapsed, the phone reduced to digits and the handful of legal symbols, the message forced to plain text with normalised line breaks
  • A honeypot field: if it comes back filled, the response is a cheerful success and nothing is sent — a bot is never told that it failed
  • Delivery is authenticated SMTPS on port 465 through PHPMailer, from a dedicated contact-form@ mailbox to the company inbox, with the sender's own address set as Reply-To — so replying from a phone answers the customer, not the form
  • The notification email is a hand-built responsive HTML table in the brand's cream palette, carrying the submission plus the timestamp, IP and user agent
  • Two production faults were found and fixed after launch, both worth naming: the form could send twice on a slow connection, and an unbounded SMTP timeout left the request hanging rather than failing

2 · After Hours — the event CRM
In June 2026 Concept Habitat ran After Hours, an invite-only evening at the showroom. A guest list on paper is a guest list nobody follows up. The brief was two sentences long: capture every visitor at the door, and be able to work the leads the morning after.

It is a React 18 + Vite 5 + React Router 6 single-page app on Tailwind CSS, backed by Supabase — Auth, Postgres, Row Level Security, Edge Functions, Realtime and Storage — deployed to Vercel with an SPA rewrite so /register/:slug and /visitors/:id resolve on a cold load. The “After Hours” look is near-black surfaces under a copper accent, and the whole token set — roughly fifty Material colour roles, the type scale, the spacing and radius scales — is lifted into tailwind.config.js, so the design system is the build rather than a stylesheet sitting next to it.

The form is configured, not coded
/register/:slug is public and carries no app chrome at all — a guest at the door sees a form, not a product. What that form asks is edited in the app:
  • Nine field types: short and long text, email, phone, number, single and multiple choice, dropdown, yes/no, checkbox
  • Each field takes a required toggle, an optional CRM mapping (“maps to” a real column, so the answer lands in the pipeline rather than in a blob), options typed by hand or sourced live from the Products / Project Stages / Lead Categories taxonomies, and conditional visibility — show this only when question X equals Y
  • Every event has its own template or inherits the global one; a new event can inherit, copy the global as a starting point, or start from scratch
  • Answers land twice: mapped fields into their real columns, and every answered question into a form_data JSONB snapshot. A question that existed on the night of the event is still readable months after the template moved on — which is the whole reason the snapshot is there
  • Unmapped custom questions are not second-class: they appear on the visitor profile, in the CSV and Excel exports, and in Analytics as categorical breakdowns
  • Each event gets a shareable link and a QR code, downloadable as PNG or JPG so it can go on a printed card at the entrance
Two triggers do the security work the UI cannot
Registration numbers are CH-AH-2026-000001, allocated from a Postgres sequence inside a before insert trigger — so two guests registering on two tablets at the same moment always get distinct numbers, and a number is never reachable from the client.

The second trigger, sanitize_public_visitor(), is the one that matters. It runs on every insert and asks a single question: is auth.uid() null? If it is, the row came from the public form, and lead rating, follow-up status, assigned staff, assignment, follow-up date and created_by are all forced back to their defaults. The public form cannot post itself a hot rating or a staff owner, whatever a crafted request contains — and the frontend does not have to be trusted to prevent it.

Three roles, enforced in the database
  • Super Admin — everything, plus the only role that can add users, set roles, deactivate accounts and reset passwords
  • Admin — the full CRM: assignment, analytics, reports, exports, event links, settings and the staff performance view
  • Staff — register and work visitors, scoped by RLS to only the visitors assigned to them
  • Anonymous users may insert a visitor and only for an active event, and may read no visitor at all. form_settings and active events are publicly readable because the form needs its own configuration — configuration only, never PII
  • The UI gates mirror the policies for a decent experience; the policies are what actually enforce them
Creating a staff account needs the service-role key, and a service-role key in a browser bundle is a service-role key in public. So “Add Staff” calls a Supabase Edge Function that verifies the caller is an active Super Admin before it touches the Admin API. Everything that doesn't need the elevated key — role changes, deactivation, password resets — keeps working whether or not that function is deployed, and the button says so rather than failing silently.

Around that: new accounts are flagged must_change_password and routed to a Set Password screen on first sign-in; Forgot password is a six-digit OTP flow (email → code → new password) driven by the {{ .Token }} reset template; branded HTML templates for signup, invite, magic link, email change and reset all live in the repo rather than only in a dashboard nobody backs up; and the seeded Super Admin is protected — it cannot be deactivated or duplicated, because an event CRM locked out of its own admin account at 7 pm is not recoverable.

Working the leads
  • Dashboard — total registrations, today's count, conversion, the hot/warm/cold split, follow-ups due and overdue, visitors by day for the last seven days, visitors by district, top interested products and project stage
  • Potential Leads — the hot and warm board, uncontacted first, because that is the only order that list is ever read in
  • Follow-Up — the pipeline: Not Contacted → Contacted → Quotation Sent → Site Visit → Closed Sale, with Won and Lost as the two ways out
  • Visitors — search plus a side-panel filter set, sortable columns, twenty-five per page, row selection with bulk export and, for admins, bulk archive
  • Visitor profile — the mapped CRM fields, every custom answer, and an append-only notes timeline where a note can carry a photo or a PDF up to 10 MB
  • Analytics — total visitors, conversion rate, most requested product, districts covered, then breakdowns by day, staff, product, district, profession and project stage
  • Reports — filter by event plus date, district, staff, status and interest; exports are named per event so three downloads in a folder are still tellable apart
  • Audit log — database triggers record every insert, update, delete and archive on visitors, events, users and settings: who, when, and a field-level before/after diff
  • Staff management, event links and settings — the taxonomy lists and the global form template
The operational details
  • CSV, Excel and PDF exports share one column definition — twenty-two columns, from registration number to follow-up date — so the three formats can never disagree about what an export contains
  • xlsx and jsPDF sit behind a dynamic import(): someone who only signs in and looks at the dashboard never downloads a spreadsheet engine
  • Deleting is archiving. Archived visitors drop out of lists, dashboards, reports, analytics and the sidebar badges, and are restored from Records → Archived. Only an admin can delete for real
  • The sidebar badges — due follow-ups, uncontacted hot and warm leads — run on Supabase Realtime, so a colleague's update on the showroom floor changes your count without a refresh
  • setup.sql is a single file that resets, recreates and seeds the entire database: schema, triggers, RLS policies, the registration sequence, the storage bucket, the realtime publication and the first Super Admin. A demo environment you cannot rebuild in one command is a demo environment nobody rebuilds
  • One bug worth naming because it is the classic one: the visitors-by-day chart bucketed on UTC and pushed every late registration into the following day. An event that runs past 8 pm in UTC+4 is exactly where that shows up. It buckets in local time now

3 · The internal mobile app
The CRM answered one evening. The business runs every day, and the parts of it that were still on paper were the parts that happen away from a desk: the site survey in a half-built house, the installation crew's sign-off, the appointment nobody wrote down. The app is Flutter 3.47 / Dart 3.13 on the same Supabase backend — Android and iOS, iOS 15 deployment target, application id mu.concepthabitat.concept_habitat. Seventeen features, thirty-six screens, twenty-two blocs and cubits, around 225 Dart files.

What it covers
  • Dashboard — role-aware landing: today's appointments, assigned jobs, live counters, quick actions
  • Visitors — showroom walk-ins and leads: capture, qualification, temperature, follow-up, and conversion into a customer
  • Customers & Projects — customer records with multiple projects each, addresses, documents, notes and an activity timeline
  • Calendar — month and week views, appointments with attendees, attachments, reminders and completion outcomes
  • Site Surveys — the guided wizard: areas, measurements, conditions, risks, products, photos, GPS and sign-off
  • Product Library — categories, products, variants, images, documents, applications, properties, accessories and related items
  • Customer Selections — what a customer chose, per customer or per project, feeding the quotation
  • Quotations — line items, discount, VAT, totals, and a status path from draft through sent to accepted or declined
  • Installations — scheduling, crew assignment, start and complete workflow, before/during/after evidence photos and sign-off
  • Inspiration Gallery — field captures linked to a customer, a project or a product
  • Reports — revenue, conversion funnel, visitor analytics, operations, product selections and employee activity
  • Notifications — an in-app centre plus Firebase Cloud Messaging and local reminders
  • Administration — employees and roles, company settings, quotation defaults and the reference picklists
Seven roles, enforced twice
Administrator, executive, operations, sales, designer, technician, delivery. Around forty-five named capabilities live in one AppPermission enum, and AppPermission.forRole is the single table that grants them. PermissionScope exposes the set, PermissionGate hides or disables the widget, and — the part that matters — the router redirects off the same table. A capability moves between roles in one place, and the navigation, the buttons and the deep links all move with it. Row Level Security in Postgres is still the real boundary; the enum mirrors it rather than replacing it.

Sign-up is disabled by design (enable_signup = false): employees are invited, never self-registered. A trigger promotes the first account to administrator and starts everyone after that as sales. Inviting needs the service-role key, so it lives in an invite-employee Edge Function that checks the caller is an active administrator first — and until that function is deployed, the Invite button explains exactly that instead of throwing, and an administrator can still invite from the Supabase dashboard. A separate role-guard trigger refuses a role change from anybody but an administrator, so the check exists even for a caller who never opens the app.

The database is the API
  • Fourteen ordered migrations, roughly 5,000 lines, 42 tables. Applied in filename order, because later files depend on earlier ones, and the last one is re-runnable reference data (on conflict do nothing)
  • Thirty-odd enums, so the business vocabulary lives in the schema rather than in string comparisons: visit sources (walk-in, After Hours, Salon de la Maison, Facebook, Instagram, website, phone call, referral), project phases (lead → site survey → design meeting → quotation → installation → completed), thirteen appointment types, twelve measurement units from mm through m³, sqft, piece, set and kg
  • Transactional workflows are database functions — convert_visitor_to_customer, complete_site_survey, start_installation, complete_installation, complete_appointment, archive_record, restore_record — so a dropped connection in a house with one bar of signal cannot leave a half-converted visitor behind
  • Quotation money is computed in the database, on a trigger: subtotal summed from the items, discount applied by percent, VAT at a rate stored per quotation and defaulted to 0.15 rather than hard-coded — so a future rate change does not silently rewrite last year's documents — each step rounded to two decimals. The app never posts a total it worked out itself
  • dashboard_summary plus six report functions (revenue, conversion, visitors, operations, product selections, employee activity) do the aggregation in Postgres, so a report screen is one round trip rather than a fan-out of queries
  • Soft deletes throughout (deleted_at), with partial unique indexes so deleting a quotation releases its reference number instead of reserving it forever
  • An activity_log and an audit_log, both written by triggers and by a shared log_activity helper — never by the client
The eight-step survey wizard
Information → Site details → Areas → Measurements → Conditions → Risks → Products → Review. Measurements hang off areas, so the measurements step sends you back to Areas when there are none rather than presenting an empty sheet and letting you wonder what you did wrong. Photos and a GPS position are captured on site, access is rated easy / moderate / difficult, risks carry a priority, products are attached straight out of the Product Library, and completion goes through complete_site_survey so the survey, its media and its status change together. Progress is persisted locally by DraftService, because a survey is taken standing up, in a building site, on a battery.

Storage, scoped by folder
Eight buckets: product-media and profile-images public; product-documents, survey-media, inspiration-media, installation-evidence, appointment-files and project-documents private. Objects are stored under a folder named after the owning record and the storage policies authorise on that folder — so a technician assigned to one job cannot read another job's evidence photos, which is the kind of thing a signed URL alone will not give you.

Failing well
  • Every repository call returns Result<T> — Success or FailureResult — and never throws. BaseRepository.guard() checks connectivity, runs the call and maps Postgres error codes to typed Failures, so a unique violation and a dropped connection arrive at the UI as two different messages instead of one “something went wrong”
  • Online-first with local drafts: connectivity is watched, an offline banner appears when it drops, writes fail with a retryable message, form and survey progress survives, and media uploads queue for retry
  • With .env still empty the app starts normally and shows a guided setup screen naming exactly what is missing — rather than crashing on a null client. It also says that .env is a bundled asset and needs a restart rather than a hot reload, which is the thing everybody gets wrong once
  • Firebase Cloud Messaging is fully wired, but until the config files exist NotificationService.pushAvailable stays false, the in-app notification centre and the local appointment reminders keep working, and nothing crashes. The Gradle plugin is applied only when google-services.json is actually present, so a fresh clone builds
Architecture and design
  • Feature-first Clean Architecture: every feature owns domain/ (entities, repository contracts), data/ (freezed models, Supabase implementations) and presentation/ (cubits, pages, widgets), and nothing reaches across a sibling's data layer. AuthBloc owns the session; every other screen is a Cubit
  • go_router with guards and a tab shell, get_it + injectable for wiring, freezed + json_serializable for the models
  • The palette is transcribed from the React prototype — near-black greens from #030806 to #0D1E14 under a gold accent #C4A452. The prototype's muted greys were too dark to read on those surfaces, so the four text tones were lifted into a visible ladder measuring 14.7:1, 6.5:1, 5.0:1 and 4.0:1 against the lightest surface: four distinguishable steps where every step still clears 4:1. text_contrast_test.dart holds those floors, so a later colour tweak fails the suite instead of quietly failing a reader
  • Raleway for headings, Nunito Sans for body, five weights each, both bundled
  • Breakpoints.of(context) classifies the window as phone or tablet, portrait or landscape: phones get a bottom navigation bar, tablets a navigation rail, grids change column count, and ContentColumn caps line length so a tablet in landscape does not render 140-character lines
  • The test suite covers what rots silently rather than what is easy to test: the permission table, quotation totals, the Result type, validators, the calendar's month grid, design-system overflow, empty-state layout, the auth screen's brand layout, and those contrast floors
  • react/ stays in the repository as the original design prototype — the reference for UI, wording, colours and flows. It is not built, not shipped, and not modified by the Flutter app

4 · One database, two vocabularies
This is the part of the project I would actually talk about in an interview.

The CRM was live, with real visitor records from the event on it, when the mobile app's schema needed to land on the same Supabase project. Both applications describe a person and a member of staff, and neither describes them the same way. The CRM has role as free text (super_admin / admin / staff) and a boolean active; the app has app_role as an enum of seven and is_active. Same rows, two languages.

The failure mode was quiet rather than loud, which is worse. The app's migrations declare profiles and visitors with create table if not exists — good practice against an empty project, and against this project it meant both statements did nothing at all. Every migration reported success and not one mobile column appeared. The app then failed later, on a screen, with a missing-column error that pointed nowhere near the cause.

20260101000150_crm_coexistence.sql is the answer, and it drops, renames and retypes nothing:
  • The missing columns are added additively to profiles and visitors and backfilled from the CRM data already sitting there
  • Two immutable mapping functions translate in both directions. map_role_to_app_role reads the CRM's role; map_app_role_to_role goes the other way and is deliberately conservative — only administrator and executive become the CRM's admin, and everything else lands on staff, because widening administrative rights is not a decision a mapping function should be making on its own
  • Triggers keep the two vocabularies in sync from then on, in both directions — a role changed in the app is a role changed in the CRM, and neither application has to know the other exists
  • The backfill runs under session_replication_role = replica, and this is the detail I am most pleased with. The CRM installs set_updated_at and audit_trigger on both tables. A plain UPDATE to backfill a column would therefore have stamped every historical updated_at with the migration's timestamp and written a phantom audit row for every visitor in the database — permanently corrupting the audit trail the CRM exists to provide, in the name of adding a column nobody had asked about. Replica mode suppresses those triggers for the migration only; the session role is restored at the end of the file
  • It is ordered explicitly: after the enums migration (it needs the types) and before the one that adds indexes and a foreign key referencing the columns it creates
  • Every added column carries a comment on column saying which application owns the vocabulary and what keeps it in sync, because the next person to read this schema will not have this page open
The result is unglamorous and exactly right: both applications still run, against one row per person, and neither had to be rewritten to accommodate the other.

There is one more note in that schema worth repeating, because it is a Supabase-specific trap and it does not announce itself: new tables inherit the project's default privileges, and those include anon. Every future table needs its own explicit revoke. RLS being enabled is not the same as anonymous access being denied — so in this schema it is denied at both the grant and the policy level.
