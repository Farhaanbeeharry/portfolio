Fruitopia

July — August 2026 Farhaan Beeharry
mobile app flutter dart supabase postgresql marketplace delivery tracking
Fruitopia is a farm-to-table marketplace for Mauritius — one Flutter binary containing two entirely different applications. Customers browse what a seller has picked today, order it, and watch the van approach their building. Sellers get a workspace: inventory, the day's list, the order queue, a delivery route they drive with the app open, broadcasts and analytics. Which application you get is decided by your account, and each side has its own navigation shell.

It is a feature-first Clean Architecture build — domain (pure Dart: entities, repository contracts, use cases), data (models and Supabase data sources), presentation (Cubits, pages, widgets), and a per-feature DI module — with flutter_bloc for state, get_it for wiring and go_router driving two StatefulShellRoute trees. Repositories return a Result<T> and never throw across the boundary; the presentation layer maps failures to localised messages. There is no mock data source: the backend is Supabase and it has to be reachable to boot, which keeps the seams honest.

1 · The daily list is the product
A greengrocer does not have a catalogue, they have a morning. The seller publishes one daily list per delivery date — a unique index enforces exactly that, so the list is upserted rather than duplicated — carrying the items, the regions it delivers to, and the delivery fee as it was at publication.

That fee snapshot matters more than it looks. The seller's own profile is not publicly readable, so a customer could not be shown a fee that lived only there; and a fee change tomorrow must not silently reprice a list customers are already ordering from today. Per-item stock is deliberately three-valued in the same spirit: NULL means "as much as you want", an integer is a real count that decrements as orders come in, and zero is sold out. "Unlimited" and "none left" are different statements and are stored differently.

2 · One customer, one bag
A customer who checks out twice for the same delivery day gets one order, not two. The seller packs one bag per customer per day and the route groups by stop, so a second row described a hand-over that never happened in real life — and split the same person's fruit across two receipts.

Placing an order is therefore a merge-or-create function, and the details are where it earns its keep:
  • It takes a transaction-level advisory lock on the customer and the delivery date. Two checkouts racing each other would otherwise both see "no open order" and insert one each — precisely the split the function exists to prevent
  • Only a pending, unpaid order for that day is joined. Anything delivered or settled is closed business, and a later order starts a fresh one
  • A new order is inserted with the cart's totals already on it rather than as zeroes patched afterwards, because the "new order" notification fires on that insert and would otherwise announce an order worth Rs 0.00
  • A merge grows an order the seller has already been told about, so the insert trigger does not fire again — a second trigger announces the top-up instead, and fruit added after the first checkout still reaches the packing list
  • The delivery point follows the latest checkout: the customer has just said again where they want it, and one merged order is one drop-off
  • The buyer is read from auth.uid() rather than trusted from the caller, so a security-definer function that must update an existing order still cannot write anybody else's

Orders carry a short human reference — FR01000 and upward from a sequence — because nobody reads a UUID down a phone line.

3 · Delivery, modelled the way it is driven
The seller defines regions, each one either office or home. An office region holds a list of buildings, so a customer ordering to work picks their building from a list instead of typing an address a driver then has to interpret; a home region falls back to a typed street address. Only active regions are offered, and each is named in both languages.

On delivery day the seller works a route of stops, and two public-read tables turn that into something the customer can watch: a per-seller, per-date delivery_progress row holding the ordered stops and which one is current, and a seller_locations row updated as the van moves. The customer's tracking screen therefore says "three stops before yours" rather than "out for delivery", on a live map. Only the seller may write either table; anyone may read them, which is what makes the tracking work without an account-by-account fan-out.

4 · Notifications that survive a replay
Every notification is a row first. A trigger then posts it to the push transport, and the row is claimed by stamping pushed_at — so a webhook delivered twice is a no-op the second time rather than a duplicate buzz, and a partial index over the unpushed rows keeps that lookup cheap. The customer's in-app inbox and the push notification are the same record, which is why they cannot disagree.

A seller broadcasting to a region hits a wall the interface cannot climb: profiles are self-read only, so the seller genuinely cannot select the customers in a region. Resolving "who is in these regions" and inserting their notifications is a security-definer function — and each row it inserts still fires the same push trigger, so the broadcast path and the ordinary path stay identical.

An abandoned-cart reminder runs on the same rails: a pending_carts row per customer per list, a scheduled job that turns the ones about to expire into notifications, and a per-customer opt-out on the profile. Both the scheduler and the HTTP extension are installed non-fatally — a project whose plan refuses them still applies the whole schema and simply logs that reminders will not be scheduled, rather than failing the migration at line 1,150.

5 · Preferences belong to the person
Small thing, deliberately done: the customer chooses where the cart button lives — a floating button, the bottom bar, or the app bar — and that choice is stored on the profile, not the device, because signing in on a new phone should put the cart back where you put it. When the default later moved from the bottom bar to the floating button, only the column default changed; everyone who had already chosen kept their choice.

What each side gets
  • Customer — today's list and category browsing, product detail with unit and quantity, favourites, a cart with a live summary and the snapshotted delivery fee, checkout against a building or a street address, order history with a short reference, live route tracking on a map, a notification inbox with push, and an account with avatar upload and in-app cropping
  • Seller — a dashboard of the day's revenue and orders, inventory with images, publishing and editing the daily list with per-item stock and a cost snapshot, the order queue with each customer's delivery point, route planning and live progress, region and building management, broadcasts by region, analytics, and settings for working days, delivery fee, contact channels and notification toggles

Engineering
  • English and French fully externalised in ARB files, generated with flutter gen-l10n; no user-facing string is hardcoded
  • Skeleton loaders shaped like the content they replace rather than spinners, so a list does not jump when it arrives
  • The schema file is safe to re-run against a live database — every statement is if not exists, create or replace or an idempotent seed. The destructive reset that once lived at the bottom of it, a delete from auth.users included, was moved into its own file: it was one editor paste away from erasing production
  • iOS ships to TestFlight from Codemagic, which rebuilds the git-ignored .env from a secret group and then fails the build if any required key is empty. That check exists because a missing map key once produced a build that ran perfectly and drew a blank tracking map on device, while local builds with the real file looked fine
  • Twenty-six test files with bloc_test and mocktail, and flutter analyze clean
