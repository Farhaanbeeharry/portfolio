MotoGate

February — September 2026 Farhaan Beeharry
mobile app flutter dart supabase postgresql qr access control motorsport
Built for MotoClub Mauritius, MotoGate replaces a clipboard at a race gate. It runs the whole lifecycle of a motorsport event — creating it, building the guest list, accepting competitor entries, issuing passes, verifying cars, and admitting people at the gate against a live database — and it carries the club's racing-licence register in the same app, because a competitor's licence and their entry pass are the same kind of credential.

It is Flutter in a feature-first Clean Architecture with BLoC. Firebase Cloud Messaging is the only Firebase service left in it; everything else runs on Supabase — PostgreSQL with Row Level Security and a set of Deno edge functions. That left is the interesting part of this case file.

1 · The ticket cannot be replayed
A pass is not a stored code that the scanner looks up. An edge function mints a short-lived signed ticket — a base64url JSON payload carrying the event, the invite, the holder's code, an issue time, an expiry five minutes out and a nonce, with an HMAC-SHA256 signature over it. The scanner sends the pair back to a second function, which verifies the signature in constant time, checks the expiry, and admits the holder exactly once.

The one-time guarantee is structural rather than procedural: the lock table's primary key is the SHA-256 of the ticket's own signature, so a replayed ticket collides on insert. There is no read-then-write window for two gate scanners to race through — a screenshot forwarded to a friend fails against the database, not against a check somebody remembered to write.

Scanning is permission-gated at the function too: the caller is identified server-side and must be an admin or hold scan_qr, so possessing the endpoint is not possessing the ability to admit people.

2 · Moving off Firestore, without a flag day
The app began on Cloud Firestore with a couple of PHP endpoints beside it, and was migrated onto Supabase. Two decisions made that survivable:
  • The ticket payload format was carried over verbatim — the same base64url JSON and the same HMAC — so tickets issued by either side stayed interchangeable through the cutover. Nobody at a gate had to care which backend had minted the pass in their hand
  • Every imported row kept its original Firestore identifier in a firebase_id column. The import is therefore idempotent and re-runnable, and any record can still be traced back to the Firebase backup — which is what makes a migration reversible rather than merely finished

The migration itself is tooling, not a weekend: a backup script with a verifier, then a numbered import pipeline — reset, auth, edge cases, data, verify, branding — followed by seven scripted smoke tests that exercise the edge functions, push, and the event, auth, guest, licence and admission RPCs against the migrated data.

3 · Three races the client used to lose
Most of the schema work was moving computations out of Dart, where two devices could each read the same state and both act on it, into single statements:
  • Licence review. The review screen ran a Firestore batch across the application, the issued licence and sometimes a renewal, with the validity date and licence number computed in Dart from a separate query. Two admins reviewing the same application could each compute a date from the same starting point and both commit. Now one function does the read, the computation and every write — and stays SECURITY INVOKER, so the guard that stops an admin approving their own application remains in force
  • Race numbers. Availability was three separate queries — issued licences, in-flight applications, pending renewals — combined in Dart, on two different screens that could drift apart. Two riders could pass the check simultaneously and both claim a number. It is now one statement, and one place
  • Gate admissions. The special-guest screen appended an invite, its companions and a scan log to arrays on the event document and bumped the entered count from a value it had just read. Both are now inserts against real tables with the counter adjusted inside the same statement, so two gate devices admitting at the same moment cannot lose a log or a count

4 · Turning Realtime off, on purpose
Every screen originally held a WebSocket to Supabase Realtime. On the free plan that allows two hundred concurrent connections against a shared instance — and every open app held one. Worse, every scan at the gate made Realtime evaluate RLS for every subscriber and made every subscriber re-download the event with all of its invites and scan logs. With a thousand members that was the one part of the system that scaled with the size of the club rather than with the number of people doing something.

So it was removed. Screens read through PostgREST and re-read on three honest triggers: the device that changed something says so, the user pulls to refresh, or the app returns to the foreground. Gate screens on a live event poll one small row instead of streaming the whole event graph. The publication was then emptied as well — a table in it costs WAL decoding on every write whether or not anyone is subscribed — and the migration that had added those tables was left in place as the record of what it used to carry.

5 · The gate
Admins create an event, set venue capacity, and manage invitees, their companions and whole teams — each assigned an access role that decides where they may go. The roles are rows, not an enum: the seven system defaults (Media, Staff, VIP, Sponsor, Services, Demo, Other) can be renamed, recoloured, re-iconed or disabled, and the club can add its own.

At the gate the scan resolves to a full-screen granted or denied result, admits the allowed number of companions against the invitee, offers a supervised override for the edge cases, and files every decision in a live entry log. A separate special-guest flow covers arrivals with no pass at all. Passes are protected against screenshots and screen recording, and lift the screen brightness so they scan first time.

6 · Competitors, not just guests
Members apply to take part in an event as a car (auto) or a rider (moto), admins decide, and an accepted participant receives the same entry pass as anybody else — because acceptance is materialised into the guest-list structures that already exist. An accepted car becomes a team row whose pilot may add a co-pilot and two mechanics; an accepted rider becomes an invite. QR issue, gate scanning, printing and export therefore needed no new code path at all, and the existing invitation flow was left untouched.

Around that sits the scrutineering the sport actually requires:
  • Two-stage car verification — a checker records the inspection with a signature, and a second person confirms it, each stamped with who and when
  • Verification slots rather than one event-wide time, with a scheduled reminder that goes out once and records that it did
  • Group assignment — an event carries its own list of groups, de-duplicated case-insensitively while preserving the order they were entered in, and a participant is assigned a group and a race number by somebody holding that permission
  • An entry deadline and explicit fee acceptance, so a competitor has agreed to what they are being charged before the entry counts
  • Every date question goes through one function that converts to Mauritius local time — event dates are stored as the UTC instant of local midnight, and casting that to a date in UTC lands on the previous day

7 · Permissions, and one licence per application
Console access is granted permission by permission: event admin, licence admin, user management, QR scanning, notifications, pricing, manual verification, car verification and group assignment. A gate steward sees only the scanner; the club secretary sees the licence queue. The set is a CHECK constraint on the profile — an unknown permission cannot be written at all, so a typo fails at the database instead of silently granting nothing.

Licences run their own lifecycle: application, review, issue, renewal, revocation with a recorded history, and the console filters by Pending, In Review, Issued, Renewals, Rejected and Revoked. Documents and photos are uploaded with in-app cropping, pricing is configurable per licence type, and the issued number keeps the club's existing format — MCL, the two-digit year, then the race number, padded — because a register people already read should not be renumbered by a rewrite.

Engineering
  • Auth, user deletion, QR issue and verify, a QR-use reset, push and the verification reminder are each a small Deno edge function; the two PHP endpoints they replaced are named in the comments so the lineage is readable
  • Access-role definitions, invite structures and scan logs are real tables with indexes rather than arrays on a document, which is what made concurrent gate scanning correct rather than merely fast
  • On-device PDF generation for printed access bracelets, and CSV or PDF export through the share sheet or a file download
  • Contact-book import when adding guests, so phone numbers are not retyped at a desk
  • A public marketing site with privacy, support and terms pages accompanies the store listings
