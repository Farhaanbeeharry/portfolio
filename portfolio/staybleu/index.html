StayBleu

April — July 2026 Farhaan Beeharry
web app hotel pms next.js 16 react 19 supabase postgresql multi-property
StayBleu is the property-management system a front desk actually stands at. One screen holds the live state of every room across every property: who is in, who is due out, who has not paid, which rooms are dirty, and what the day has taken. It is built for the Mauritian short-stay market, where a room is not only sold by the night — the same room is sold for a day, for an evening, for a day and an evening, or for several nights with a day tacked on either end.

The stack is Next.js 16 / React 19 with Tailwind CSS 4 on Supabase — Auth, PostgreSQL with Row Level Security, and nothing else in between. Every mutation is a typed Server Action (src/app/actions/, ten files and roughly three thousand lines), so the browser never holds a privileged key and the audit entry is written on the same code path as the change it describes.

The stay type is derived, not chosen
A receptionist enters a check-in and a check-out. They never pick a tariff. The six stay types — day use, evening use, day + evening, full stay, full stay + evening use, full stay + day use — are computed from the two timestamps against the day window (08:00–17:00): a same-day booking that starts before five and ends after eight touches the day, one that runs past five also touches the evening, and one that opens before eight has already touched the evening before it. The price follows from the type, and the type follows from the clock. A desk under pressure cannot pick the wrong rate, because it is not offered one.

Room pricing is stored the way it is quoted: day_use_price and evening_use_price are the two real numbers, and full_day_price is their sum, recomputed rather than entered — a third editable number is a third number that can disagree with the other two, and a full day that does not equal its own halves is an argument at the desk. Birthday rates are a separate, nullable set: NULL means this room has no birthday tariff at all, which is a different statement from zero, and clearing the amenity clears all three birthday columns with it.

Overstaying is charged, and it is still not a status
Nothing in the schema records that a guest is late. The extra charge is derived at the moment somebody looks: a day use that has crossed 17:00 attracts the evening price, an evening use still in the room after 08:00 the next morning attracts the day price, and a full stay attracts a further day either past noon on its checkout day or four hours past its planned checkout on any other day. Because it is derived, an overstay resolves itself the moment the guest leaves, and it can never be left behind as a stale flag on a room that has since been cleaned and re-let.

Check-out is then intercepted rather than blocked. If payment is still pending, or the stay has crossed into a chargeable range, the action stops and raises the payment sheet with the extra already calculated. The member of staff can still complete the check-out — they simply cannot complete it without having been shown the number.

What a booking will not let you do
  • Double-book a room. The overlap check ignores cancelled and checked-out rows, and treats a checked-in stay with no actual_check_out as occupying the room indefinitely — the guest is in there, and a planned departure that has passed is not evidence that they left
  • Cancel a stay that has already happened. A Confirmed booking cancels freely; a Checked-in one only within fifteen minutes of arrival, which covers the mis-scan and excludes the rewrite; a Checked-out one never
  • Check in without settling how the money is being handled — a pending payment raises the same interception on the way in as on the way out
  • Reach a property that is not yours. profiles.locations scopes every list, and asking for a location you are not assigned to returns an empty set rather than an error, so the filter cannot be used to enumerate the estate

Who sees which bookings
Booking visibility is three-valued rather than boolean: none, today, anytime. A today scope is deliberately not "bookings whose check-in date is today" — that hides the guest who arrived yesterday and is leaving this morning, who is precisely the person a morning shift needs. It is every stay whose window overlaps today, measured against the actual check-out where one exists and the planned one where it does not.

Guests are people, not rows on a reservation
A guest record carries a national ID, a passport number and a driving licence, each independently unique, so the same person checking in on a different document is still the same person. Guests link to one another as parent and child — a constraint refuses a guest as their own parent, and the pair is unique, so a family cannot be recorded twice. A ban carries its reason. Addresses typed at the desk are normalised into a shared suggestion table, so the fourth guest from the same block of flats does not arrive with a fourth spelling of it.

At booking creation each adult signs on the screen. The signatures are stored as a JSON object on the booking keyed by guest id, so a party of four produces four attributable signatures on one reservation rather than one signature standing in for everybody.

Two things the database refused to leave to the interface
Roles are rows, not an enum. A role holds a JSONB permission map, and one function — check_permission(module, action), security definer — resolves the caller's role from their profile and asks whether that module's array contains that action. Nearly every write policy in the schema is that call and nothing else, which is why adding a role is a row rather than a migration.

A later hardening pass closed two holes the interface had been quietly covering:
  • The finance ledger had policies, but RLS had never been enabled on the table — so the policies were inert, and the blanket authenticated grant let any signed-in user read and write the whole ledger. The policies looked right in a diff and did nothing at runtime
  • RLS cannot restrict individual columns, so the "you may edit your own profile" policy also let a user set their own role to Admin. A BEFORE UPDATE trigger now rejects any change to role, super_admin or is_revoked unless the caller holds users.edit — with an explicit service_role bypass, so the trusted server paths still work

Two factors, and a session that can be taken away
A password gets you an e-mail OTP, and only verifying it sets the second-factor cookie the middleware demands alongside a valid session. Two details make it behave: an authenticated, verified user is redirected away from the auth screens in the middleware, so the login page never flashes on a hard refresh; and every request re-reads is_revoked with the service-role client, so disabling an account ends its session on the next navigation rather than whenever its token happened to expire.

Signing out is a cash-up
Pressing sign out does not sign you out. It shows the shift you just worked — bookings created, income, expenses, refunds, the net, and the split across cash, card and MCB Juice — and only then ends the session, writing that summary to cashier_sessions against the session token it belonged to. The handover conversation at the end of a shift now has a number in it, and the number was not typed by the person handing over.

Around the desk
  • Dashboard — active stays, checkouts due, occupancy and pending payments, per property or across all of them
  • Locations — a Leaflet map and a table view, each property carrying its own amenities, policies and accepted payment methods, with the room count maintained by a trigger rather than by whoever last edited a room
  • Finance — one ledger for income, expenses and refunds, numbered and attributable, with booking payments landing in it on the same code path that takes them
  • Housekeeping — tasks by type and priority, and a trigger that moves the room's own status as the task moves
  • Reports — revenue, occupancy, and an estimate of the unpaid overstays sitting in rooms right now
  • Audit log — every privileged action, with a field-level before/after diff rendered as a sentence rather than a JSON blob

Engineering
  • The audit table deliberately keeps user_id and location_id as plain columns with no foreign keys. An audit trail that cascades away when you delete the user it accuses is not an audit trail
  • The diff summariser ignores id, created_at and updated_at, and phrases a cleared field as "was removed" rather than "changed to empty" — to the person reading the log those are two different events
  • "Today" is a start-of-day / end-of-day pair built once and passed down rather than recomputed per row, so a list cannot disagree with itself about which day it is halfway through rendering
  • English and French throughout via next-intl, with the language stored on the profile — the same shared terminal serves a French and an English receptionist on consecutive shifts
  • Room photos and avatars are cropped in the browser before upload, so the desk is not pushing a 12 MP phone photo up a hotel's connection
