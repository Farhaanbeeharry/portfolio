NexStock

July — September 2026 Farhaan Beeharry
web app mobile app laravel 12 react flutter postgresql modular monolith
NexStock is a business operating system for small and medium enterprises — one platform in place of the usual pile of disconnected tools. Multi-branch inventory, a point of sale, quotations and invoicing, customers and suppliers, purchasing, accounting, reporting and audit sit in a single system, configurable enough to fit a retail shop, a wholesaler, a workshop, a garage, a printer or a repair business. It is built for Mauritius and francophone markets first — Rupees, UTC+4, French as a first-class language — without being unable to leave them.

There are three deliverables: a Laravel 12 API, a React + TypeScript SPA for the back office and the POS, and a Flutter companion app for the shop floor. The mobile app is not a shrunk-down dashboard: it is designed for one hand while standing, a camera instead of a keyboard, and a stockroom with poor light and a worse connection.

1 · A modular monolith, with the boundaries enforced
The API is a single deployable application partitioned into fifteen business modules, each owning its domain end to end — HTTP, rules, persistence, migrations, events, tests — behind a small published surface. Inside each one, a light Domain / Application / Infrastructure split: entities, value objects and contracts that know nothing of the framework; use-case actions that orchestrate them; Eloquent models, controllers, policies and gateways underneath. api/app/ is a composition root and nothing else — business logic arriving there means it is in the wrong directory.

The modules are tiered, and the tiers are the dependency policy: a shared kernel of primitives; a platform tier (Auth, Users, Settings, Notifications); master data (Products, Customers, Suppliers) that consumers may read but only its owner may write; the transactional core (Inventory, Purchasing, Sales/POS); and downstream modules (Accounting, Reporting) that declare no dependency on an operational module at all and subscribe to domain events instead. That last rule is what makes a new report addable — and the accounting module removable — with zero edits to Sales or Inventory.

The graph is a DAG and it is checked rather than trusted: Deptrac fails the build on any violation or cycle. It also excludes test scaffolding and factories on purpose — a factory reaching for another module's entity to build a fixture says nothing about the production dependency graph, and quietly widening deptrac.yaml to accommodate a test would cost the boundary its meaning. Contracts speak in DTOs and value objects, never Eloquent models: a model leaking across a module boundary would recreate exactly the coupling the structure exists to avoid.

Four gates run as one command — Pint for formatting, Larastan at level 6, Deptrac for boundaries and PHPUnit, with the suite split into a thin App shell and per-module tests. All four pass, and the repository's working agreement is explicit that if you cannot keep them passing you say so rather than leaving a gate red without comment.

2 · What the platform actually does
Roughly eighty-six migrations, owned by the module that needs them rather than pooled centrally:
  • Inventory — branches and per-branch stock, stock movements, adjustments with reason codes, inter-branch transfers with their own line items and a cancellation reason, and expiry batches
  • Products — categories, units of measure, variants and variant attributes, images, tags, and customer-definable custom fields as definitions plus values rather than as columns
  • Sales — quotations that convert into invoices, invoice items with their own status, payments, credit and debit notes, a processing queue for workshop and repair jobs, and held POS orders so a sale can be parked and resumed
  • Purchasing — purchase orders and goods receipts, each with line items, so what was ordered and what arrived are separate facts
  • Accounting — a chart of accounts with journal entries and journal lines, fed by events from the operational modules
  • Users — roles, permissions and their pivots, login histories, trusted devices, invitations, and per-user theme and language
  • Settings — payment methods, API keys, webhook endpoints, an activity log with batch UUIDs, and asynchronous data export and import requests
  • Support — document templates and generated documents, plus the audit log

3 · The two halves have contracts nothing enforces at build time
The frontend and backend share rules that no compiler checks, so they are written down as non-negotiables:
  • Clients branch on error_key, never on message text. A client that matches on prose breaks the first time the copy is improved or translated
  • The password policy is defined once on the client — both the Zod schema and the on-screen checklist derive from the same constant — so keeping it in step with the API rule is a one-line change rather than a hunt
  • Removing a form field means removing its validation rule too. Dropping password_confirmation from the UI while leaving Laravel's confirmed rule in place produces a silent 422 that looks like nothing happened
  • The two-factor branch returns 202 with a session token, not an error. The client has to treat it as a success shape, which is exactly the sort of thing a contract document exists to say out loud

Authentication is JWT with two-factor by e-mail OTP or an authenticator app, trusted devices so a returning phone is not challenged again, and account lockout. There are seven auth screens, and one deliberately unfashionable detail on the sign-up form: the password requirements box is always visible rather than revealed on focus. A checklist that only appears while the field is focused cannot be read while you are typing into it, which is the only moment it is useful.

4 · Two test blind spots, written down because they cost real time
Green tests are necessary and not sufficient here, and both structural blind spots are documented in the repository rather than rediscovered:
  • actingAs() bypasses the auth user provider. A broken auth.providers.users.model passes every test in the suite and returns 401 on every authenticated HTTP request in production. One real request has to be smoke-tested
  • Notification::fake() never renders the mail template. A Blade error or a missing translation key is invisible to it. The view gets rendered, or read in Mailpit, before the change is called done

A third, smaller one earns its place beside them: after editing a queued job, listener, notification or mail view, the queue worker has to be restarted. It is long-running and holds classes in memory, so skipping that means debugging the previous version of your own file.

5 · Transactional e-mail is 2003 on purpose
Templates use table-based layouts, bgcolor and inline styles, with a plain-text alternative generated for every message. Modernising them with flexbox, grid or <picture> breaks Outlook and the Gmail app, and forcing a white logo onto a dark background through a prefers-color-scheme media query produces invisible white-on-white in Apple Mail. The logo is therefore a universal teal that needs no dark-mode variant at all — which is the same argument the whole palette is built on.

6 · The palette is an accessibility argument, not a mood board
The brand comes from the mark: a cyan accent (#04dde2) over a teal ink (#0d9488), with interactive surfaces running teal → cyan. Blue appears nowhere in the logo, so it was retired from the brand entirely and now means status.

The shades were then chosen by measurement. There is a narrow band of relative luminance — roughly 0.118 to 0.30 — inside which a colour clears 3:1 against both white and near-black, and so can be used on either ground. Teal 600 sits in it with the best worst case of the candidates (3.74:1 on white, 5.39:1 on slate 950). But 3.74:1 does not reach the 4.5:1 that text needs, so anything carrying white text — buttons, the active nav pill, badges, tab triggers — uses the 700 shades at 5.4:1, and 800 on hover. Teal 600 stays correct where only 3:1 applies: checkbox ticks, switch thumbs, progress fills, and large bold headings.

One CSS rule is banned outright. A bare [data-state=…] selector once existed, and because it was unscoped it made every closed Radix component in the application invisible but still clickable — which is a far worse failure than a visibly broken one, and took three attempts to diagnose from static reading before somebody reproduced it in a browser.

7 · The account, not the device
Theme and language follow the account, carried in a JWT claim, so a fresh device adopts the right settings on first login and shared shop hardware does not force the next person to reset it. On the API side the user model implements Laravel's locale preference, which is what makes a background notification or a queued e-mail arrive in the language the recipient chose rather than the language of whoever triggered it; anonymous mail, such as a signup OTP, passes its locale explicitly because there is no user yet to ask.

Engineering
  • The SPA develops against a Mock Service Worker layer that mirrors the real response envelope, so a screen can be finished before its endpoint exists without hard-coding a shape the API will not send
  • API boundaries are validated with Zod schemas in features/*/api/contracts/, so a shape change is caught where it enters the client rather than three components later
  • Eloquent models carry @property docblocks generated from the live schema rather than hand-written, because Larastan at level 6 requires them and a hand-written one drifts
  • $fillable has to mirror the table in both directions: a missing column is silently dropped, and a phantom column fails at the database
  • Every document in api/docs/ and web/docs/ carries a "known gaps" section, and the working agreement is explicit — if the code and a document disagree, trust the code, fix the document in the same change, and say so. Documentation that lies is worse than none, because it gets trusted
