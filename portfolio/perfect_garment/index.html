Perfect Garment

September 2026 Farhaan Beeharry
mobile app flutter supabase postgresql 3d mockup invoicing manufacturing
Perfect Garment is the internal Android application for Perfect Making, a Mauritian garment workshop that cuts, prints and embroiders custom clothing to order. Before it existed an order lived in a notebook, a quotation was retyped into Word, the deposit was remembered rather than recorded, and whether a job was late depended on who you asked. The app replaces that whole chain with one record: the order is taken in front of the customer, the quotation is generated and sent from the same screen, the deposit is receipted against it, the promised date is tracked, the invoice is raised on delivery, and the money is reported at the end of the month.

It is built with Flutter in a feature-first Clean Architecture — BLoC/Cubit for state, go_router for navigation, get_it + injectable for wiring — on a Supabase backend: Auth, PostgreSQL with Row Level Security, and private Storage buckets. There is no server of my own in between. The database is the API, and every business rule that matters is enforced inside it.

The order lifecycle
An order moves through eight named states, and the app never invents a ninth. Draft → Quotation pending → Awaiting deposit → Confirmed → Delivered → Completed, with Rejected and Cancelled as the two ways out. Each transition is one PostgreSQL function — generate_quotation(), approve_quotation(), record_payment(), mark_delivered(), generate_invoice(), cancel_order() — which validates the move, writes the new status and appends the audit entry in a single transaction. A half-applied transition is not something the app has to defend against, because the database will not produce one.

Delayed is deliberately not a status. Lateness is derived from the promised date, so reporting a slip revises the date and files the reason in delivery_changes — it never overwrites where the order actually is. A confirmed order that is a week late is still confirmed; the operational flag sits beside the state rather than on top of it.

Document numbering that cannot be argued with
Quotations are PGQ001… and invoices PGI001…, drawn from two independent PostgreSQL sequences allocated inside the generating function. Two devices raising a quotation at the same moment always receive distinct numbers, a number is never reused — not even when the quotation it belonged to is later rejected — and the sequences are not reachable from the client at all, so a document number cannot be spoofed or skipped from a phone. Past 999 the format simply continues (PGQ1000).

Artwork and the 3D mockup
Switching a placement on in the item editor gives it an Upload control. The picked file (gallery or camera, PNG/JPG/WEBP, up to 10 MB) goes straight to a private artwork bucket under a random path, and the placement stores only that path — so the same file feeds the preview and the production floor without ever being duplicated. Replacing artwork deletes what it replaced; turning a placement off deletes its file too.

Orders containing a t-shirt, polo or cap then gain an extra wizard step between Delivery and Review: a turnable 3D garment — the supplied .glb at full mesh resolution — rendered in the order's own main and contrast colours, with each uploaded artwork applied to the surface it will actually be printed on. Drag to rotate, pinch to zoom, or open it full screen, because a sleeve print is only a few hundred pixels inside a card.

The details of that step are the whole point of it:
  • Colour is reported, not flattered — the viewer is pinned to neutral tone mapping at exposure 1.0, because the default filmic curve returns a chosen navy desaturated and lifted, and the customer is approving a colour
  • Left and right are the wearer's, mirrored on the front view — the convention a print shop already uses
  • A cap is decorated on the front panel only. The editor offers one switch for it and the entity refuses any other placement, so no code path can promise something the workshop cannot make
  • The step is a check, not a gate: artwork often arrives after the price is approved, so a placement with no file is flagged in a banner and outlined with a dashed frame — it never blocks the quotation
  • The mockup is an internal production aid. It does not appear on the quotation or the invoice, and neither does an artwork path or filename
  • A build step (tools/build_models.mjs) prepares the raw exports losslessly and adds the one thing that makes the feature possible — a print surface per placement, since the source UVs are tiled fabric coordinates that cannot carry a logo
  • The models render entirely offline; the viewer and its assets are served from inside the app, so a workshop with no signal still gets the preview

One customer, however many orders
A customer is identified by phone number or email, never by name. Saving an order looks for an existing customer on either before inserting, so a returning customer is updated rather than duplicated and every order they have placed hangs off one record. Phone matching normalises first — digits only, compared on the last eight, the length of a Mauritian subscriber number — so +230 5421 8890, 5421 8890 and 230-5421-8890 are one person. The newest details win on a match, with one exception: a blank never overwrites something already on file, because an order taken without an email must not erase the address captured last time.

Getting the document to the customer
Every generated PDF offers three routes, and the file and its message always travel together — a WhatsApp intent with the PDF attached, the staff member's own mail app pre-filled with recipient, subject, body and attachment, or the system share sheet as the fallback. No external mail provider, no API key, no server-side sending: the email leaves from the staff member's own address and stays in their Sent folder like any other message.

The mail route is the part that needed real work. MainActivity.kt asks Android which apps can handle a mailto: address and restricts the intent to those, which is what makes it open a mail app instead of a generic share list. One mail app installed and it opens straight on the compose screen; several and the intent carries a mailto: selector so the system lists them all (EXTRA_INITIAL_INTENTS is deliberately avoided — Android 12 caps it at two entries, which would silently hide a third mail app); none and it falls back to the share sheet rather than failing. Each candidate is granted read access to the attachment through the app's FileProvider first, so the PDF always attaches. Every shared document is also copied to a private bucket in the background, so there is a record of exactly what the customer received — best-effort, and a storage hiccup never blocks a share.

The security model
  • RLS is enabled and forced on every business table; anonymous access is denied at both the grant and the policy level
  • Authenticated staff have read-only direct table access. Every write goes through a SECURITY DEFINER function that validates the transition, moves the status and writes the audit entry in the same transaction
  • No privileged secret ships in the APK. .env carries only the project URL and the publishable key — a service-role key in a Flutter app would be a service-role key in every customer's hands
  • There is no public sign-up. Staff accounts are created by an administrator, and a profiles row is bootstrapped by a trigger so the audit trail always has a name to print
  • A note in the schema flags the trap for whoever comes next: new tables inherit Supabase's default privileges, which include anon, so every future table needs its own revoke

What never reaches the customer
Payments carry an internal White / Black classification for the owner's own accounting. It — along with audit entries, staff identities, database ids and artwork storage paths — is excluded from every generated PDF: from the visible text, from the document metadata, and from the filename. The app says so on screen wherever the classification is captured, and the PDF builders read from the saved order rather than from form state, so a document can never disagree with the database.

Configured by the business, not by the build
The company name, tagline, location, phone, email, trading address, BRN and bank details are not in .env — they belong to the business, not to the build. They live in a single-row company_settings table, edited in the app under Profile → Company details, so a correction reaches every device without a new APK. Document filenames follow the company name, so renaming the business renames the files. Bank lines print individually and each is omitted when blank — the IBAN is still to be issued, and an invoice reading IBAN: — invites a question nobody wants to field.

Where a garment is configured
Each garment is worked through in one pass — Specification → Quantities → Customisation → Pricing — and the last tab hands the order on to the delivery date. Quantities sit beside the specification because that is where the size grid is chosen; two tabs away, choosing a grid looked like it did nothing. Pricing sits with the garment rather than in a step of its own, so a configuration is specified, counted, decorated and priced without being returned to. The domain then refuses the combinations the workshop cannot make: a t-shirt is cut from 160 or 180 GSM jersey and a polo from 220 GSM pique, a cap is bought made up and so has no fabric section at all, nobody orders a medium cap so caps are counted as a single total, and a contrast colour is offered only where there is a knitted collar or cuff to run it in. Female counts are capped at the total in three separate places — the stepper, the entity and save_order — because the male count is derived from the difference and an uncapped value would mean a negative number of men.

Beyond the order
  • Dashboard — pending quotations and what they are worth, orders awaiting a deposit, confirmed, late, due this week, the next delivery date, and the month's money in and out, all in one round trip
  • Calendar — a month view of every delivery-bearing order with a day agenda, so a promised date is looked at rather than remembered
  • Finance — received against expenses for any period, filterable by transaction type, with expense capture in the app
  • Tasks — three states and no more, grouped Overdue / Due today / This week / Later / No deadline / Finished, because a deadline list is read in one order and a flat list makes the reader work that order out themselves
  • Audit timeline — every privileged action, who did it and what it changed, readable per order

Engineering
  • Feature-first Clean Architecture: each feature keeps domain/ (entities, repository contracts), data/ (Supabase implementations) and presentation/ (cubits, pages, widgets) separate. Business rules live in the domain layer and in the database — never in widgets
  • Money is Decimal end to end, never a double, because a rounding drift on a quotation is a rounding drift on a bill
  • Adding an @injectable class means re-running build_runner, and forgetting is invisible to the analyzer — it only throws when that screen is opened. A dependency-graph test cross-checks every getIt<T>() call site against the generated registrations, so the suite fails instead of the user
  • The whole schema is reproducible from versioned migrations, concatenated into one readable schema.sql by a script rather than by supabase db dump, so regenerating it does not depend on Docker being up
  • A widget-test suite covers the parts that quietly rot: business rules, PDF generation, wizard flow and autosave, the mockup and its textures, model assets, stepper and keyboard layout, and a design-parity test that holds the theme to the design canvas
  • Typography is Instrument Sans for prose and IBM Plex Mono for anything numeric or referential — money, document numbers, dates, quantities — both bundled, so rendering is identical offline and inside generated PDFs
