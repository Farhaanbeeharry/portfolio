MoMento

January — July 2026 Farhaan Beeharry
web app angular 20 supabase postgresql webgl planning poker project delivery
MoMento is a delivery platform built around the one artefact most teams already produce and then abandon: the minutes of a meeting. A meeting is written up with its agenda, attendees and decisions; the actions agreed in it become tickets that keep a link back to the meeting that created them; the tickets run through a Jira-shaped board with sprints, story points and a hierarchy; and the estimating itself happens inside the product, at a live planning-poker table.

It is an Angular 20 application — standalone components, signals, lazy routes, Angular Material and the CDK — on a Supabase backend. Everything is scoped to a project, and membership is the only key: two security-definer helpers, is_project_member() and is_project_owner(), are what nearly every Row Level Security policy in the schema actually calls, so "can this person see this" is answered in one place rather than restated per table.

1 · From a meeting to a ticket
Minutes are structured, not a text box: an agenda whose items carry an order and a duration, a list of decisions, and attendees as real member rows rather than typed names. An action item can hold mom_id, so months later a ticket still answers "where did this come from" — and the foreign key is on delete set null, because deleting the write-up should not delete the work it produced.

2 · The board
Action items are the largest surface in the application by a wide margin — one component of roughly 7,700 lines of TypeScript against 6,400 of template. An item carries a ticket key, an issue type (Epic · User Story · Feature · Bugfix · Task), a status (Backlog · To Do · In Progress · Testing · Blocked · Done), a priority, an assignee and a reporter, labels, story points, an hours estimate, start and due dates, an order index for manual ranking, and a parent — so an epic genuinely contains its stories rather than merely being tagged alongside them. Every one of those vocabularies is a CHECK constraint, so an unknown status cannot arrive through the API and quietly widen the board.

Deletion is a timestamp and an author (deleted_at, deleted_by), never a DELETE. A ticket removed by mistake in a sprint-planning session is recoverable, and the audit of who removed it survives.

The denormalised sprint name, and why it is safe
An item stores both sprint_id and the sprint's name. That is a duplication on purpose: the board groups, filters and exports by name constantly, and carrying the name means those paths never need the join. The usual cost of denormalisation — the copy going stale — is removed by two triggers rather than by discipline: one fills the name from the id on every insert and update, the other rewrites every affected item when a sprint is renamed. Renaming "Sprint 4" to "Hardening" is a single update, and no ticket is left pointing at a sprint that no longer goes by that name.

3 · Planning poker, at a real table
Estimation is a live, project-scoped session anyone on the team can watch or join. A room owns its card scale (0 1 2 3 5 8 13 21 ? coffee by default, and editable), whether the cards flip automatically, and a reveal countdown of nought to thirty seconds. A round walks Voting → Revealing → Revealed, and every transition is a PostgreSQL function; the client asks, it never decides.

The interesting rules are the ones about what a player is allowed to know and when:
  • Cards are unreadable until the round flips. The read policy is gated on poker_round_is_revealed(), so "don't render it yet" is not what is keeping your estimate private
  • A seat still publishes has_voted — the fact that a card is down, never which card — which is what drives the face-down card at each seat and the waiting-on-N counter
  • A vote can only be cast while the round is still collecting them. Once the reveal starts the table is final until the host calls a re-vote, so nobody can nudge their number after seeing everyone else's
  • Only the host may flip early — but anyone may trigger the automatic reveal once every eligible seat has voted, so a round is not held hostage by a host whose tab has gone to sleep
  • Spectators are a real role and are excluded from the "everyone has voted" count, so a watching manager cannot stall the table
  • Averages ignore ? and coffee rather than coercing them to zero, which would drag consensus down every time somebody admitted they did not know
  • Agreeing a number pushes it onto the linked ticket — the estimate lands on the work, not in a chat log

Two performance details keep the room quiet: recomputing the has_voted flags only touches rows that actually change, so realtime subscribers are not woken for nothing; and a trigger touches the room row whenever one of its children changes, so every lobby and dashboard watching the room updates from one small write rather than by re-reading the session.

The table itself is hand-written WebGL
The seats, the cards and the buttons stay in the DOM — crisp text, real focus rings, screen-reader-navigable. Everything underneath them is a thousand-line WebGL 1 renderer with no external dependency at all: the felt and its padded rail lit by a single overhead lamp, the ripple every vote drops into the surface, a radar sweep while the table is still waiting, arcs that tighten into the countdown, a shockwave on the flip, consensus confetti, and emoji that players throw at each other along a bezier arc — swelling as they cross the middle so the throw reads as height rather than a slide. The felt warms toward red as disagreement across the revealed cards widens. If a WebGL context cannot be created, the component falls back to the painted CSS table and the room carries on.

4 · Documents
Project documents are a block editor with the full tool set — headings, lists, checklists, tables, quotes, warnings, code, embeds, images, attachments, toggles and undo — organised into folders. Two things lift it above a wrapper around a library:
  • A custom block tune records who last edited each block, and when, showing the recent authors with their avatars in the block's own menu. Attribution is per paragraph, not per document
  • Versions are immutable snapshots of the title and content. The table has no UPDATE policy at all — a version cannot be edited into saying something it never said — and only its own author may delete one
  • Markdown pasted in is parsed to blocks with a pre-pass that repairs the most common real-world defect: an unindented continuation paragraph after a list item, which every naïve parser turns into a separate paragraph and which is re-merged into the list item it belongs to

5 · Money, and the rest
  • Financing — a project has a price per percentage point, each member a contribution percentage and a start date, and monthly payment rows unique per member per month. Members read; only the owner writes
  • Expenses — dated project expenses with a non-negative constraint, on the same read-all / owner-writes split
  • Calendar — the delivery dates the board implies, as a month view
  • Team and invitations — invite by e-mail, inspect the invitation before accepting, and accept it, all through security-definer RPCs rather than direct table writes
  • Settings and theme — light and dark throughout, with the logo swapped per theme rather than recoloured by a filter

What "recently active" actually means
A project's updated_at is maintained by triggers on everything that belongs to it — minutes, action items, documents, sprints, labels, members, payments — and a meeting's updated_at the same way from its agenda, decisions and attendees. So sorting the project list by activity reflects the last thing anybody did in it, not the last time somebody happened to edit the project's own name. It is a small amount of trigger plumbing that makes an ordinary list stop lying.
